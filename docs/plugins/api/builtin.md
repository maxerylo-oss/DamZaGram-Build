# `dzg.builtin` и команды всех плагинов

Модуль `builtin` делает две вещи:

1. **Ставит встроенные плагины.** Клиент несёт внутри себя плагины из
   `plugins/builtin/` и при каждом запуске раскладывает их в
   `tdata/plugins/<id>/`. Что они умеют — в [builtins.md](../builtins.md).
2. **Связывает команды плагинов.** `dzg.commands.all()` видит слеш-команды
   всех загруженных плагинов, а `dzg.commands.run()` выполняет любую из них.
   На этом построена командная палитра (Ctrl+K).

Типы: [`types/builtin.d.ts`](../types/builtin.d.ts). Исходник:
`Telegram/SourceFiles/damza/plugins/api/api_builtin.cpp`.
Автор — [@wetakush](https://t.me/wetakush).

| Метод | Что делает | Результат |
|---|---|---|
| `dzg.builtin.list()` | Встроенные плагины и что с ними сделал установщик | `BuiltinPluginInfo[]` |
| `dzg.commands.all()` | Команды всех загруженных плагинов | `PluginCommandInfo[]` |
| `dzg.commands.run(text, chat?)` | Выполнить команду любого плагина | `boolean` |

```js
// Все команды клиента, сгруппированные по плагинам.
const byPlugin = {};
for (const c of dzg.commands.all()) {
  (byPlugin[c.pluginName] ||= []).push('/' + c.name);
}
console.log(byPlugin);

// Сделать ИИ-дайджест текущего чата из своего плагина.
dzg.commands.run('/digest 100');
```

`run` вызывает обработчик команды напрямую: сообщение никуда не
отправляется, `onBeforeSend` других плагинов не срабатывает. Команда
получает обычный контекст: `args`, `rest`, `text`, `chat` и `replyTo = 0`.
Свою команду плагин выполняет сам, чужую — через клиент: если тот плагин
прямо сейчас выполняет JS (например, вызвал нас же), `run` вернёт `false`.

## Как работает установка

На старте (`appStarted` модуля, до сканирования папки плагинов) для
каждого встроенного плагина:

- папки `tdata/plugins/<id>/` нет или в ней нет `manifest.json` —
  плагин ставится;
- в установленном `manifest.json` есть `"builtin": true` и его `version`
  меньше вшитой (semver: `1.2.0 > 1.1.9`, `1.0.0 > 1.0.0-beta`) —
  файлы перезаписываются, `manifest.json` пишется последним;
- в установленном `manifest.json` **нет** `"builtin": true` — это плагин
  пользователя с тем же id, клиент его не трогает;
- папка — символьная ссылка (например, на `plugins/builtin/<id>` в
  репозитории для живой разработки) — клиент ничего в неё не пишет;
- плагины, у которых в манифесте нет `"enabledByDefault": false`,
  включаются, если пользователь ещё ни разу не включал и не выключал их сам.

Удалить встроенный плагин нельзя: при следующем запуске он вернётся.
Его можно выключить — этот выбор сохраняется. Чтобы навсегда заменить
встроенный плагин своим, убери из его `manifest.json` строку
`"builtin": true` или подними версию.

## Как добавить встроенный плагин (для разработчиков клиента)

1. Создай `plugins/builtin/<id>/` с `manifest.json` (`"id"` = имя папки,
   `"version"` в semver, `"builtin": true`, `"author": "@wetakush"`) и
   `main.js` (ES-модуль).
2. Напиши тест `tools/damza/tests/builtins/<id>.test.js` и прогони все:
   `tools/damza/tests/builtins/run.py` (можно `run.py <id>`). Тест
   запускается в песочнице с моками из `tools/damza/tests/builtins/_setup.js`,
   значения настроек по умолчанию берутся из манифеста; объект `mock`
   даёт панели, уведомления, отправленные сообщения, историю чатов и т. п.
3. Запусти `tools/damza/embed_builtins.py`: он упакует все файлы в
   `Telegram/SourceFiles/damza/plugins/builtin/builtin_files.cpp` (строки
   кусками меньше 16 КБ — ограничение MSVC). Флаг `--check` проверяет,
   что сгенерированный файл свежий.
4. **Подними `version`**, если меняешь уже выпущенный плагин, — иначе у
   пользователей останется старая копия.
